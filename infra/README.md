# AlphaPro OMS — Terraform

Infrastructure-as-code for the AlphaPro Order Management System (Shopify →
EventBridge → SQS → ECS Fargate). Reconstructed from the original state file and
parameterized so the same module deploys both **dev** and **prod**.

See `../awsterrafrom/INFRASTRUCTURE.md` for a full description of what gets built.

## Layout

```
infra/
├── modules/alphapro/         # the reusable infrastructure module (all resources)
│   ├── versions.tf          # required providers
│   ├── variables.tf         # all inputs
│   ├── locals.tf            # name prefix, tags, store×queue matrix
│   ├── connections.tf       # computed DB/cache connection strings
│   ├── network.tf           # VPC, subnets, IGW, NAT, routes
│   ├── security.tf          # security groups + rules
│   ├── data_stores.tf       # RDS PostgreSQL + ElastiCache Valkey x2
│   ├── secrets.tf           # random password + Secrets Manager
│   ├── iam.tf               # ECS execution/task roles & policies
│   ├── alb.tf               # ALB, listener, target group
│   ├── ecs.tf               # cluster, tasks, services, autoscaling
│   ├── messaging.tf         # SQS (+DLQ) + EventBridge rules/targets
│   ├── monitoring.tf        # log group, SNS, 18 alarms
│   ├── storage.tf           # S3 assets bucket
│   └── outputs.tf
└── environments/
    ├── dev/                 # dev root: module call + .env + tf.sh wrapper
    └── prod/                # prod root: same module, prod .env
```

Each environment is an independent Terraform root (separate state). They share
one module, so a change to the module applies to both after review.

## Configuration via `.env`

Most environment-specific configuration lives in `environments/<env>/.env` as
`TF_VAR_*` variables. The `tf.sh` wrapper sources `.env` (exporting every key)
and then runs `terraform`, so Terraform picks the values up automatically.
Simple lists (e.g. CIDR blocks, the capacity provider strategy) are JSON,
single-quoted.

`.env` is git-ignored; `.env.example` is the committed template.

**Exception: `stores`.** Store config (name, app URL, and one Shopify
EventBridge bus per queue type) is not in `.env` — it lives in
`environments/<env>/stores.auto.tfvars`, one HCL block per store, in the same
file for that environment's whole store list. Terraform loads it
automatically (the `.auto.tfvars` suffix means no `-var-file` flag needed).

To add a new store, copy an existing block in that file, change the key and
every value, and set up its 3 EventBridge buses (inventory/orders/products)
in AWS first. No `.tf` file changes — every SQS queue, DLQ, EventBridge rule,
consumer service, and alarm for that store is generated automatically from
this one block, the same way it already is for `ksa` and `uae`. A
copy-paste-ready example block (for "kwt" / Kuwait) is included as a comment
in the file.

`stores.auto.tfvars` is git-ignored the same way `.env` is;
`stores.auto.tfvars.example` is the committed template.

## Prerequisites

- Terraform >= 1.5
- AWS credentials in your shell (`aws configure` / `AWS_PROFILE` / SSO)
- The ECR image referenced by `TF_VAR_container_image` must exist
- (Recommended) An S3 bucket + DynamoDB table for remote state — see
  `backend.hcl.example`

## Usage

```bash
cd infra/environments/dev      # or prod

./tf.sh init                   # first time
./tf.sh plan
./tf.sh apply
./tf.sh output
```

Or from `infra/` with the Makefile:

```bash
make validate ENV=dev
make plan ENV=dev
make apply ENV=prod
make fmt
```

### Remote state (recommended for prod)

Dev and prod each get their **own** S3 bucket for state — `squatwolf-alphapro-dev-tfstate`
and `squatwolf-alphapro-prod-tfstate` — not one shared bucket with different key
prefixes, so a mistake in one environment's state operations can't reach the
other's. They do share one DynamoDB lock table
(`squatwolf-alphapro-terraform-locks`), which is safe: the lock table's key
includes the bucket name, so dev and prod locks never collide there.

None of these three resources (2 buckets + 1 table) exist yet — create them
manually first (they're exactly the kind of thing Terraform can't create for
the backend it's about to use), then per environment:

```bash
cp backend.hcl.example backend.hcl   # edit values if you changed the names
# uncomment `backend "s3" {}` in versions.tf
./tf.sh init -backend-config=backend.hcl
```

## Secrets

- The **database password** is generated by Terraform (`random_password`) and
  stored in Secrets Manager (`<project>/<env>/database`).
- The **Shopify secret** (`<project>/<env>/shopify`) is created empty. Populate
  it out-of-band (console/CLI) — the version's `secret_string` is set to
  `ignore_changes`, so applies won't overwrite it. To seed it from Terraform,
  set `TF_VAR_app_secret_value` to a JSON string.

## Database ownership (`db_host`)

Leave `TF_VAR_db_host` **empty** (both dev and prod) to have Terraform create
and manage the RDS instance: it generates the master username/password,
creates the `<project>/<env>/database` secret, and owns the instance going
forward. This is the default for both environments.

`db_host` exists only as an escape hatch for adopting a database Terraform
doesn't yet manage — e.g. one that was hand-created, or created by an older
version of this config. Setting it makes Terraform **skip** the RDS instance,
parameter group, subnet group, and secret entirely, and just read the
existing `<project>/<env>/database` secret (data source) for the credentials
ECS consumes.

Prefer bringing that database under management with `terraform import`
instead of leaving `db_host` set indefinitely — an unmanaged database has no
`prevent_destroy` protection, no Terraform-tracked backup/retention settings,
and drifts silently from the module's config. To import an existing instance:

```bash
cd infra/environments/dev
# db_host must be empty in .env before this plan, or Terraform tries to
# reuse instead of create/manage.
terraform import 'module.alphapro.aws_db_subnet_group.this[0]'      <subnet-group-name>
terraform import 'module.alphapro.aws_db_parameter_group.this[0]'   <parameter-group-name>
terraform import 'module.alphapro.aws_db_instance.this[0]'          <db-instance-identifier>
terraform import 'module.alphapro.aws_secretsmanager_secret.database[0]'         <project>/<env>/database
terraform import 'module.alphapro.aws_secretsmanager_secret_version.database[0]' '<secret-arn>|AWSCURRENT'
terraform plan   # read every proposed change before applying
```

`random_password.db[0]` cannot be imported (RDS never returns the master
password via its API), so the first `plan` after import will show a new
random password being generated and applied to the instance — a real,
in-place credential rotation, not just a state change. Coordinate an ECS task
restart right after that apply so tasks pick up the rotated secret; until
they restart, they're still holding the old password in their running
environment.

Also review every other attribute in the plan before applying — a mismatch
on an immutable attribute (identifier, engine, master username) would force
a replace, which `prevent_destroy` on `aws_db_instance.this` (see
`data_stores.tf`) will correctly refuse rather than silently deleting data,
but you want to catch that in `plan`, not find out from an apply error.

The deployer's IAM principal needs the obvious `rds:*`/`secretsmanager:*`
create-and-manage permissions for this path. The narrower
`secretsmanager:DescribeSecret` + `secretsmanager:GetSecretValue` +
`ec2:DescribeAvailabilityZones` set is only sufficient for the `db_host`-set
(unmanaged, reuse-only) path.

## Fargate capacity (Spot vs on-demand)

ECS services take their capacity from `capacity_provider_strategy`, not
`launch_type`. The module default is **100 % `FARGATE_SPOT`** (base 1, weight 1),
which is what the live dev stack runs. `environments/prod/.env` overrides it to
on-demand `FARGATE`, since Spot tasks can be reclaimed with a two-minute warning.

Set the variable to `[]` to inherit the cluster's default strategy instead.

## Notes on prod defaults

The prod `.env` is hardened (Multi-AZ DB, deletion protection, final snapshot,
replicated Valkey, larger tasks, private DB, on-demand Fargate) and uses a
separate VPC CIDR (`10.1.0.0/16`). Review the event bus ARNs and app URLs — they
assume a `-prod` naming convention and must match your actual Shopify prod
integration.
